# Pusher 新推送服务开发文档（以内置 Bark 为简单示例、企业微信为复杂示例）

> 本文档面向想要为 Pusher 添加「新内置推送服务」的开发者。
> 全文用两个**真实的内置服务**贯穿：
> 简单示例用 **Bark**（内置、最精简，适合照抄模板），
> 复杂示例用 **企业微信**（内置，覆盖异步 token、每应用覆盖等全部进阶写法）。
> 读完本文档，你应该能照着这套流程在 30 分钟内接入任意一个新的推送服务。

---

## 1. 怎么读这份文档

- **不打底子，直接照抄**：跳到 [第 3 章] 看 Bark 这个最小样板，然后照 [第 5 章] 的
  流程把 `NSPBarkService` 复制一份改名，改三个地方（服务名、URL、body）即可。

目标读者需要的基础：熟悉 Objective-C、了解 Theos 构建、能看懂 iOS 越狱 tweak 基本结构。

## 2. Pusher 是怎么推送的（架构速览）

### 2.1 数据流

```
SpringBoard 收到一条系统通知
        │
        ▼
Tweak.xm 里的 BBServer hook (sendBulletinToPusher:)
        │
        ▼
NSPusher.handleBulletin:   ← 入口,单例
   ├─ 全局预置过滤 (NSPushFilter / globalAppList / 锁屏&网络条件)
   ├─ 防循环 (PUSHER_LOOP_PREVENTION_WINDOW=25, THRESHOLD=10, 滑动窗口)
   └─ 逐服务分发 sendToService:  (只发给已启用的服务)
        │
        ▼
服务类 (实现 NSPPushService 协议)
   ├─ infoDictForBulletinContext:config:  → 组装请求体
   ├─ headersForConfig:                   → 组装认证 Header
   └─ URLStringForConfig:completion:      → 组装最终 URL(可能异步)
        │
        ▼
NSPushRequestSender   ← 统一发送器
   ├─ 失败重试 (PUSHER_TRIES=5, 网络错误间隔 1 秒 / 图片过大间隔 3 秒)
   ├─ 图片过大自动缩小重发
   └─ NSPushLog 记录每一步日志
```

### 2.2 代码地图（与本章节相关的文件）

| 文件 | 职责 |
| --- | --- |
| `Core/NSPushService.h` | `NSPPushService` 协议 + `NSPushServiceBase` 基类 + `NSPushServiceManager` 注册表 |
| `Core/NSPushService.m` | 基类默认实现、共享 data dict 构建、注册表逻辑 |
| `Core/Services/` | 每个内置服务一个 `NSP<Xxx>Service.h/.m`，**新服务放这里**（Bark、Wechat 等都在） |
| `Core/NSPusher.m` | 入口，`sendToService:` 逐服务流水线 |
| `Core/NSPushConfig.m` | 读取 Preferences 并组装 `NSPushServiceConfig`（含调用 `urlForEventName:`） |
| `Shared/NSPushPrefsStore.h/.m` | 集中读写 `com.noahsaso.pusher` 的 CFPreferences；`BuiltInServices` / `CustomServices` / `Global` 嵌套读、写、删除和写后通知都走这里 |
| `Shared/NSPushLogStore.h/.m` | 集中读写日志域 `com.noahsaso.pusher~log`；Core 的日志写入和设置里的日志页读取共用同一套 API |
| `Core/NSPushRequestSender.m` | 实际发 HTTP 请求（POST JSON body / GET query + 重试） |
| `Core/NSPushConstants.h` | 通用常量（重试次数、SNS 字段名、prefs key 名等），Core 层自包含 |
| `Core/NSPBBServer.h` | 通知入口与 BBServer 相关定义 |
| `Generated/BuiltinServices.generated.h` | 构建期自动生成：import 所有内置服务头文件并给出 `BUILTIN_PUSHER_SERVICES` 名单 |
| `Preferences/Resources/<服务名>.plist` | 每个服务的设置界面布局（`Bark.plist` / `Wechat.plist`） |
| `Preferences/NSPSharedSpecifiers.m` | 每应用覆盖字段的注册（只有需要时才改，如 Wechat 的 `touser`） |
| `Preferences/NSPSharedSpecifiers+ServiceBuilders.m` | 按服务构建动态 specifier（设备 / 声音 / 每应用覆盖入口） |
| `Preferences/NSPDeviceSoundListController.m` 及其子类 | 设备 / 声音列表的公共基类与 `NSPDeviceListController` / `NSPSoundListController` 拆分 |
| `Preferences/NSPLocalization.h` | `NSPLocalizedString()` / `NSPushServiceDisplayName()` 本地化入口 |
| `Preferences/NSPPSListControllerWithColoredUI.m` | 重写 `loadSpecifiersFromPlistName:target:`，对静态 plist 的 label / footer / validTitles 做本地化 |

> 服务名/URL 宏已下沉到各自的 `NSP<Xxx>Service.h`，不放在 `global.h`；
> `global.h` 现在只是 tweak / Preferences 的 UI 侧伞头文件。

### 2.3 服务的「注册制」——为什么加服务不用碰核心代码

Pusher 的服务是**自注册**的，核心代码对你零依赖：

1. 每个服务类在 `+load` 里调用
   `[NSPushServiceManager registerServiceClass:self forName:[self serviceName]];`
2. `NSPushServiceManager` 维护一个 `name -> Class` 的字典；
   查不到名字时兜底返回 `NSPCustomService`（自定义服务）。
3. `Makefile` 用通配符编译 `Core/*.m` 和 `Core/Services/*.m`，
   **新增 `.m` 文件不需要改 Makefile**。
4. `Preferences/NSPServiceListController` 遍历 `BUILTIN_PUSHER_SERVICES` 生成服务列表，
   只要服务名出现在名单里，设置里就自动出现入口。
5. `BUILTIN_PUSHER_SERVICES` 是**构建期自动生成**的：每次构建前
   `scripts/generate_builtin_services.sh` 扫描 `Core/Services/NSP*Service.h`
   里各服务自己的 `PUSHER_SERVICE_*` 名字宏，自动生成
   `Generated/BuiltinServices.generated.h`（它同时 import 所有内置服务
   头文件并给出名单）。**import 列表和名单都不需要手工维护**。

所以「添加一个新内置服务」本质只有两件事：**写一个类** + **在类自己的头文件里声明
名字宏**（import 和名单自动跟上），外加一份可选的设置界面 plist。

### 2.4 Shared Store 层：谁读写 Preferences / 日志

Pusher 把「偏好设置」和「日志」各做成一个独立的 CFPreferences 域：

| 域 | bundle id | 内容 |
| --- | --- | --- |
| 偏好设置 | `com.noahsaso.pusher` | `BuiltInServices` / `CustomServices` / `Global` 嵌套结构 |
| 日志 | `com.noahsaso.pusher~log` | 每个服务一个 `<service>Log` 数组 |

`Shared/NSPushPrefsStore.h/.m` 和 `Shared/NSPushLogStore.h/.m` 是这两块数据的
**唯一读写入口**。之前 Core 和 Preferences 各自直接 `CFPreferencesCopyValue` /
`CFPreferencesSetValue`，容易漏通知、错 key、类型不统一；现在全部收口到这两个
无 UI 依赖的类里，所有访问器都对 nil / 类型错误安全。

#### NSPushPrefsStore API 速览

| 方法 | 作用 |
| --- | --- |
| `preferenceValueForKey:` / `setPreferenceValue:forKey:shouldNotify:` | 读 / 写顶层 key |
| `snapshot` / `applySnapshot:removeKeys:shouldNotify:` | 整表快照 / 批量写回并删除旧 key（迁移用） |
| `builtInServices` / `customServices` / `global` | 取三大顶层容器的 nil-safe 副本 |
| `serviceForName:isCustomService:` / `setService:forName:isCustomService:shouldNotify:` | 读 / 写 / 删除一个服务的嵌套对象 |
| `customAppPrefsForService:customAppID:isCustomService:` / `setCustomAppPrefs:...` | 读 / 写一个 per-app override |

使用规范：

- **Preferences 界面层**（`NSPSharedSpecifiers`、各列表控制器）通过
  `NSPushPrefsStore` 读写，`shouldNotify:YES` 会在写后自动
  `notify_post("com.noahsaso.pusher/prefs")`，SpringBoard 里的 Core 会收到刷新。
- **Core 层**（`NSPushConfig`、迁移代码）也走 `NSPushPrefsStore`，不要再手写裸
  `CFPreferences` 调用；新代码请直接引用 `Shared/NSPushPrefsStore.h`。
- 传 `nil` 的 `serviceObj` / `appPrefs` 表示删除该服务 / 该 per-app override，
  而不是写入空对象。
- 取回来的字典都是不可变副本；要修改先 `mutableCopy`。

示例：改一个内置服务的字段

```objc
NSMutableDictionary* serviceObj =
    [[NSPushPrefsStore serviceForName:@"Bark" isCustomService:NO] mutableCopy];
serviceObj[@"serverURL"] = @"https://push.example.com";
[NSPushPrefsStore setService:serviceObj
                     forName:@"Bark"
             isCustomService:NO
                shouldNotify:YES];
```

#### NSPushLogStore API 速览

| 方法 | 作用 |
| --- | --- |
| `snapshot` | 日志域全量快照 |
| `logSectionsForService:` | 取某服务日志数组（传 `@""` 表示全局日志） |
| `setLogSections:forService:shouldNotify:` | 替换某服务日志数组，可选发 `PUSHER_LOG_PREFS_NOTIFICATION` |
| `removeLogsForService:` / `removeAllLogs` | 清单个 / 清全部日志（不发通知，由调用方刷新 UI） |

写日志的 Core 侧（`NSPushLog`）和看日志的 Preferences 侧（`NSPLogController`）
都用它，因此新增日志功能时不要自己拼 `<service>Log` key。

### 2.5 本地化机制

Preferences bundle 跑在系统「设置」进程里，`NSLocalizedString` 默认查 main bundle
是拿不到 Pusher 自己的翻译表的，所以项目里统一用 `Preferences/NSPLocalization.h`：

```objc
NSPLocalizedString(@"Key:", nil)     // 查 Preferences bundle 的 Localizable.strings
NSPushServiceDisplayName(@"Bark")    // 服务内部 key -> UI 显示名
```

- 翻译文件：`Preferences/Resources/zh-Hans.lproj/Localizable.strings`。
  格式是 `"英文 key" = "中文翻译";`，**新增文案就往这个文件加**；
  没有对应翻译时 `NSPLocalizedString` 直接返回 key 本身（英文兜底）。
- 静态 plist override：`NSPPSListControllerWithColoredUI` 重写了
  `loadSpecifiersFromPlistName:target:`，会把每个 specifier 的
  `label` / `footerText` / `validTitles` 以及页面 `title` 自动过一遍
  `NSPLocalizedString`。所以 **plist 源文件里继续写英文**，显示时自动变中文。
- 服务显示名：存储和 plist 文件名仍用英文服务名（`Bark`、`Wechat`），
  UI 要显示中文时用 `NSPushServiceDisplayName(service)` 转一下。
  新增服务后记得在 `Localizable.strings` 加一条 `"你的服务英文名" = "中文名";`。
- 动态生成的 specifier（`NSPSharedSpecifiers+ServiceBuilders` 里的
  `Receiving Devices`、`Touser` 等）也直接调用 `NSPLocalizedString`，
  所以它们不需要额外 override。

### 2.6 Device / Sound 列表拆分结构

接收设备（Devices）和提示音（Sounds）不再是散落在各个控制器里的一大坨逻辑，
而是拆成「一个公共基类 + 两个薄子类 + 一组 builder」。

| 文件 | 职责 |
| --- | --- |
| `NSPDeviceSoundListController.m` | 公共基类：从 prefs 加载 `devices` / `sounds` 数组、生成开关 cell、单选逻辑、保存到 `NSPushPrefsStore`、拉取更新骨架 |
| `NSPDeviceListController.m` | 设备模式：`isSoundMode=NO`；Pushbullet 单选；Pushover/Pushbullet 各自的 footer 和远端设备拉取 |
| `NSPSoundListController.m` | 声音模式：`isSoundMode=YES`；强制单选；Pushover/Pushbullet 各自的远端声音拉取 |

存储格式：服务对象里的 `devices` 或 `sounds` 是一个字典数组，每项形如
`{ "name": "iPhone", "id": "...", "enabled": @YES }`；per-app 覆盖时存到
`customApps[<appID>][devices|sounds]` 里。

入口如何生成：`NSPSharedSpecifiers+ServiceBuilders.m` 的 `+pushover:` /
`+pushbullet:` 会返回指向 `NSPDeviceListController` / `NSPSoundListController`
的 `PSLinkCell`，并带上 `service` / `isSound` / `isCustomApp` / `customAppIDKey`
等属性。需要给新服务加「设备 / 声音列表」时，照这两个 builder 加一个即可，
然后在 `NSPSharedSpecifiers get:withAppID:isCustomService:` 里注册分支。

## 3. 简单示例：Bark（内置，最小样板）

### 3.1 为什么拿 Bark 当「最简单」样板

Bark 是仓库里最小的内置服务（`.m` 只有 52 行），且 API 极简：

- 一条 `POST`，无 OAuth、无签名、无回调；
- 认证就是 URL 路径里的一个 device key（`https://api.day.app/<key>`）；
- 请求体只需要 `title` 和 `body` 两个字段；
- 唯一的额外点：支持自定义 `serverURL`（自建 Bark 私服），
  顺便演示了「服务特有字段」怎么写。

Bark 用到的协议方法只有 **4 个**，恰好是最小可用集：

| 方法 | 用途 |
| --- | --- |
| `+load` + `+serviceName` | 注册进服务注册表 |
| `+urlForEventName:dbName:serverURL:` | 读配置阶段拼 URL 模板（含 REPLACE_KEY 占位符） |
| `+URLStringForConfig:`（同步版） | 发送前把 REPLACE_KEY 替换成用户填的 key |
| `+extraPrefsForName:servicePrefs:` | 声明服务特有字段 `serverURL` 并给默认值 |
| `+infoDictForBulletinContext:config:` | 组装请求体 `{title, body}` |

### 3.2 Bark 的 API

```
POST https://api.day.app/<device_key>

Body (application/json):
{
  "title": "通知标题",
  "body":  "通知内容"
}
```

结论：**device key** 放 URL 路径 → 用通用字段 `key` 存；
**私服地址** → 服务特有字段 `serverURL`，自己声明（见 3.3）。

### 3.3 代码走读：NSPBarkService.h（常量就在自己头文件里）

`Core/Services/NSPBarkService.h`（完整文件，就这么短）：

```objc
#import "../NSPushService.h"
#import <Foundation/Foundation.h>

// 1) 服务名宏(必须全局唯一,同时用于 Preferences 里的 BuiltInServices key
//    和 plist 文件名)
#define PUSHER_SERVICE_BARK @"Bark"

// 2) URL 模板宏:写死默认服务地址。REPLACE_KEY 是约定的占位符,
//    最终由服务的 URLStringForConfig: 在发送时替换成用户配置的 key。
#define PUSHER_SERVICE_BARK_URL @"https://api.day.app/REPLACE_KEY"

@interface NSPBarkService : NSPushServiceBase
@end
```

**到这里常量就定义完了，import 和名单都不用你管。** 构建时
`scripts/generate_builtin_services.sh` 会自动扫 `PUSHER_SERVICE_BARK` 这个宏，生成
`Generated/BuiltinServices.generated.h`（自动 import `NSPBarkService.h`、并把
`@"Bark"` 加进 `BUILTIN_PUSHER_SERVICES`），这个名单同时驱动：

- 服务注册表的枚举
- Preferences 服务列表界面（NSPServiceListController）
- 配置快照加载（NSPushConfig）

> 原理：脚本只认「`#define PUSHER_SERVICE_XXX @"..."` 且名字不以 `_URL`/`_APP_ID`
> 结尾」的宏，所以你可以在头文件里随便加 URL / APP_ID 等变体，不会误进名单。
> 企业微信的 `PUSHER_SERVICE_WECHAT_URL` 就是这样被自动排除的。

> `REPLACE_KEY` 是项目里的通用约定（Feishu、Pushover 都用它）。
> 需要多个占位符的服务可以自定，如 IFTTT 用 `REPLACE_EVENT_NAME`、
> Pusher Receiver 用 `REPLACE_DB_NAME`、企业微信用 `REPLACE_DYNAMIC_KEY`。
> 规则：**URL 模板里写什么占位符，`URLStringForConfig:` 里就替换什么。**

### 3.4 代码走读：NSPBarkService.m（核心文件，逐段讲解）

```objc
#import "NSPBarkService.h"
#import "../../helpers.h"        // XStr / XEq / XLog 宏
#import "../NSPushConfig.h"      // NSPushServiceConfig
#import "../NSPushSupport.h"     // NSPBulletinContext

@implementation NSPBarkService

// ---------------------------------------------------------------
// 注册:进程启动时 +load 会跑,把本类挂进 NSPushServiceManager。
// 注意要写 [self serviceName],不要硬编码字符串,保持单一事实来源。
// ---------------------------------------------------------------
+ (void)load {
  [NSPushServiceManager registerServiceClass:self forName:[self serviceName]];
}

// 注册名:必须与 NSPBarkService.h 的宏一致(大小写敏感),
// 同时决定 Preferences 里 plist 的文件名,见 3.5。
+ (NSString*)serviceName {
  return PUSHER_SERVICE_BARK;
}

// ---------------------------------------------------------------
// URL 模板构建:在「读配置阶段」被 NSPushConfig 调用,生成服务的基础
// url 存进 servicePrefs[@"url"]。serverURL 非空时用于自建 Bark 私服。
// 返回的字符串可以继续保留 REPLACE_KEY,发送前才会被替换。
// ---------------------------------------------------------------
+ (NSString*)urlForEventName:(NSString*)eventName
                      dbName:(NSString*)dbName
                   serverURL:(NSString*)serverURL {
  NSString* finalURL = nil;
  if (serverURL && serverURL.length > 0) {
    if ([serverURL hasSuffix:@"/"]) {
      finalURL = [serverURL stringByAppendingString:@"REPLACE_KEY"];
    } else {
      finalURL = [serverURL stringByAppendingFormat:@"/REPLACE_KEY"];
    }
  } else {
    finalURL = PUSHER_SERVICE_BARK_URL;
  }
  return finalURL;
}

// ---------------------------------------------------------------
// 最终 URL:发送前调用。基类会以同步方式调用它;一般服务实现这一个
// 同步方法就够了(异步进阶写法见 4.5 企业微信例子)。
// 这里把用户填的 device key 替换进 REPLACE_KEY。
// ---------------------------------------------------------------
+ (NSString*)URLStringForConfig:(NSPushServiceConfig*)config {
  NSString* key = config.rawPrefs[@"key"];
  NSString* url = config.rawPrefs[@"url"] ?: @"";
  return [url stringByReplacingOccurrencesOfString:@"REPLACE_KEY"
                                         withString:key ?: @""];
}

// ---------------------------------------------------------------
// 服务特有预置字段:除了通用模板外,每个服务可以声明自己的字段。
// 返回值会被合入 config.rawPrefs(发送时可直接读取)。
// Bark 只有一个 serverURL(私服地址,默认官方服务)。
// ---------------------------------------------------------------
+ (NSDictionary*)extraPrefsForName:(NSString*)name
                      servicePrefs:(NSDictionary*)servicePrefs {
  return @{
    @"serverURL" : servicePrefs[NSPPreferenceServiceServerURLKey]
        ?: @"https://api.day.app"
  };
}

// ---------------------------------------------------------------
// 请求体:Bark 的 JSON body 只需要 title / body。
// 想带更多上下文(设备名、应用名、日期、图标、图片)的话,
// 直接 [[super infoDictForBulletinContext:config:] mutableCopy]
// 再裁剪/追加,详见 7.2。
// ---------------------------------------------------------------
+ (NSDictionary*)infoDictForBulletinContext:(NSPBulletinContext*)context
                                     config:(NSPushServiceConfig*)config {
  return @{@"title" : context.title ?: @"", @"body" : context.message ?: @""};
}

@end
```

**Bark 没实现的方法**（全部走基类默认值，见 [第 6 章] 速查表）：

- `headersForConfig:` → 默认 `@{}`（Bark 不需要 Header 认证）；
- `URLStringForConfig:completion:`（异步）→ 基类自动包一层调用同步版；
- `extraCustomAppPrefsForName:` → 默认 `@{}`（Bark 不支持每应用覆盖）；
- `loopPreventionAppID` → 默认 `@""`（Bark 没有自己的 iOS App，不会循环）；
- `shouldIncludeIconForConfig:` / `shouldIncludeImageForConfig:` → 默认 NO。

### 3.5 Bark 的设置界面：Preferences/Resources/Bark.plist

`NSPServiceController` 会按**服务名**加载 `Preferences/Resources/<服务名>.plist`
（所以文件名必须等于 `PUSHER_SERVICE_BARK`，即 `Bark.plist`）。
结构（当前 `Bark.plist` 的实际内容）：

```xml
<dict>
	<key>items</key>
	<array>
		<!-- Credentials 组:通用字段 key(device key) -->
		<dict>
			<key>cell</key>
			<string>PSGroupCell</string>
			<key>label</key>
			<string>Credentials</string>
		</dict>
		<dict>
			<key>cell</key>
			<string>PSEditTextCell</string>
			<key>detail</key>
			<string>PSDetailController</string>
			<key>defaults</key>
			<string>com.noahsaso.pusher</string>
			<key>PostNotification</key>
			<string>com.noahsaso.pusher/prefs</string>
			<key>key</key>
			<string>key</string>          <!-- 字段名,写入 BuiltInServices[Bark][key] -->
			<key>service</key>
			<string>Bark</string>        <!-- 必须等于 serviceName -->
			<key>label</key>
			<string>Key:</string>
			<key>noAutoCorrect</key>
			<true/>
		</dict>

		<!-- Options 组:服务特有字段 serverURL + footer 说明 -->
		<dict>
			<key>cell</key>
			<string>PSGroupCell</string>
			<key>label</key>
			<string>Options</string>
			<key>footerText</key>
			<string>Leave empty to use the official default server.</string>
		</dict>
		<dict>
			<key>cell</key>
			<string>PSEditTextCell</string>
			<key>detail</key>
			<string>PSDetailController</string>
			<key>defaults</key>
			<string>com.noahsaso.pusher</string>
			<key>PostNotification</key>
			<string>com.noahsaso.pusher/prefs</string>
			<key>key</key>
			<string>serverURL</string>   <!-- 字段名,写入 BuiltInServices[Bark][serverURL] -->
			<key>service</key>
			<string>Bark</string>
			<key>label</key>
			<string>Server URL:</string>
			<key>noAutoCorrect</key>
			<true/>
		</dict>

		<!-- Apps 组:黑白名单 + 应用列表(每个内置服务都有的标准段,
		     直接从 Bark.plist 复制即可) -->
		<dict>
			<key>cell</key>
			<string>PSGroupCell</string>
			<key>label</key>
			<string>Apps</string>
		</dict>
		<!-- appListIsBlacklist 的 PSSegmentCell + App List 的 PSLinkCell
		     (NSPAppListController),照抄 Bark.plist 即可 -->
	</array>
	<key>title</key>
	<string>Bark</string>
</dict>
```

> plist 里每个输入框的 `key` 就是存进 `BuiltInServices[Bark][<key>]` 的字段名，
> 服务类里 `config.rawPrefs[@"..."]` 读的就是它。`service` 必须与服务名一致。
> 最稳的做法：**复制 `Bark.plist` 改名再改字段**（[第 5 章] 的流程就是这么干的）。

**Bark 配置字段说明**：

| 字段 | plist `key` | 是否必填 | 说明 |
| --- | --- | --- | --- |
| Device Key | `key` | 必填 | 官方 Bark 的推送 device key，发送时替换 URL 里的 `REPLACE_KEY` |
| 私服地址 | `serverURL` | 可选 | 留空使用官方 `https://api.day.app`；填自建 Bark 服务地址，`urlForEventName:dbName:serverURL:` 会拼成 `serverURL/REPLACE_KEY` |

> 通用字段（`enabled`、`appList`、`appListIsBlacklist` 等）不属于 Bark 特有配置，
> 由基类和设置页统一处理；Bark 使用者只需要关心上面两个字段。

### 3.6 小结：一个「简单服务」= 5 个方法 + 1 个 plist

| Bark 实现的东西 | 对应文件 |
| --- | --- |
| `PUSHER_SERVICE_BARK` / `PUSHER_SERVICE_BARK_URL` 宏 | `NSPBarkService.h` |
| `+load` 注册、`+serviceName` | `NSPBarkService.m` |
| `+urlForEventName:dbName:serverURL:`（URL 模板） | `NSPBarkService.m` |
| `+URLStringForConfig:`（同步替换 REPLACE_KEY） | `NSPBarkService.m` |
| `+extraPrefsForName:servicePrefs:`（serverURL） | `NSPBarkService.m` |
| `+infoDictForBulletinContext:config:`（body） | `NSPBarkService.m` |
| 设置界面（Key + Server URL + Apps 段） | `Preferences/Resources/Bark.plist` |

**这就是最低配**。如果你的目标服务只是「一个 URL + 一个 key + 一个 JSON body」，
照抄 Bark 就够了。如果你的服务需要 token、每应用覆盖、类型转换等，
往下看企业微信。

## 4. 复杂示例：企业微信（内置，进阶样板）

### 4.1 为什么拿企业微信当「复杂」样板

企业微信（`NSPWechatService`）是仓库里功能最全的内置服务之一，
覆盖了协议里**几乎所有**扩展点：

| 扩展点 | 企业微信怎么用 |
| --- | --- |
| **异步 URL** | 发送前要先 `GET gettoken` 拿 `access_token`（带缓存），覆写异步 `URLStringForConfig:completion:` |
| **多个服务特有字段** | `extraPrefsForName:` 声明 corpid / corpsecret / agentID / touser 四个字段 |
| **每应用覆盖** | `extraCustomAppPrefsForName:` 让用户按 App 单独指定 `touser` 接收人 |
| **请求体类型转换** | `agentid` 必须是整数 `NSNumber`，字符串会被企业微信 API 拒收 |
| **失败语义** | 拿不到 token 时回调 `nil` 而不是空串，避免带着必败的 URL 去发请求 |
| **设置界面复杂度** | plist 里除了输入框还有 `App Customization` 入口 + Options 说明段 |

### 4.2 企业微信的 API

```
1) 取 token:
GET https://qyapi.weixin.qq.com/cgi-bin/gettoken?corpid=<CORPID>&corpsecret=<SECRET>
   → { "errcode": 0, "access_token": "xxx", "expires_in": 7200 }

2) 发消息:
POST https://qyapi.weixin.qq.com/cgi-bin/message/send?access_token=<TOKEN>

Body (application/json):
{
  "touser":  "Tom|Jerry",          // 或 "@all"
  "msgtype": "text",
  "agentid": 1000002,              // 必须是整数,不是字符串!
  "text":    { "content": "标题\n内容" },
  "safe":    0
}
```

结论：**corpid / corpsecret** → 服务特有字段（认证凭证）；
**access_token** → 每次发送前动态获取，塞进 URL 的 `REPLACE_DYNAMIC_KEY`；
**agentID / touser** → 服务特有字段，其中 `touser` 还支持每应用覆盖。

### 4.3 常量与注册

`Core/Services/NSPWechatService.h`（完整文件）：

```objc
#import "../NSPushService.h"
#import <Foundation/Foundation.h>

#define PUSHER_SERVICE_WECHAT @"Wechat"
#define PUSHER_SERVICE_WECHAT_URL                                              \
  @"https://qyapi.weixin.qq.com/cgi-bin/message/send?access_token="            \
  @"REPLACE_DYNAMIC_KEY"

@interface NSPWechatService : NSPushServiceBase
@end
```

与 Bark 的差别只有一个：URL 模板里的占位符叫 `REPLACE_DYNAMIC_KEY` 而不是
`REPLACE_KEY`——因为它不是用户配置的静态值，而是运行时动态获取的 token。
替换逻辑在异步方法里做（见 4.5）。

```objc
+ (void)load {
  [NSPushServiceManager registerServiceClass:self forName:[self serviceName]];
}

+ (NSString*)serviceName {
  return PUSHER_SERVICE_WECHAT;
}

// URL 模板不需要拼 serverURL/eventName,直接返回常量(REPLACE_DYNAMIC_KEY
// 保留到发送前才替换)。
+ (NSString*)urlForEventName:(NSString*)eventName
                      dbName:(NSString*)dbName
                   serverURL:(NSString*)serverURL {
  return PUSHER_SERVICE_WECHAT_URL;
}
```

### 4.4 服务特有字段 + 请求体

```objc
// ---------------------------------------------------------------
// 服务特有预置字段:企业微信一口气声明了 4 个。
// 返回值合入 config.rawPrefs,发送时通过 config.rawPrefs[@"corpid"] 等读取。
// ---------------------------------------------------------------
+ (NSDictionary*)extraPrefsForName:(NSString*)name
                      servicePrefs:(NSDictionary*)servicePrefs {
  return @{
    @"corpid" : servicePrefs[NSPPreferenceServiceCorpidKey] ?: @"",
    @"corpsecret" : servicePrefs[NSPPreferenceServiceCorpsecretKey] ?: @"",
    @"agentID" : servicePrefs[NSPPreferenceServiceAgentIDKey] ?: @"",
    @"touser" : servicePrefs[NSPPreferenceServiceTouserKey] ?: @""
  };
}

// ---------------------------------------------------------------
// 请求体:企业微信的 message/send 需要 touser / msgtype / agentid / text / safe。
// 两个值得注意的细节:
//   1) touser 留空时回退到 "@all"(发给企业全部成员);
//   2) agentid 必须是整数——plist 里用户填的是字符串,这里做 NSNumber 转换,
//      否则 API 会报 invalid parameter。
// ---------------------------------------------------------------
+ (NSDictionary*)infoDictForBulletinContext:(NSPBulletinContext*)context
                                     config:(NSPushServiceConfig*)config {
  NSString* touser = config.rawPrefs[@"touser"];
  NSNumber* agentid = config.rawPrefs[@"agentID"];
  NSInteger agentIDValue = 0;
  if (agentid) {
    agentIDValue = agentid.integerValue;
  } else if ([config.rawPrefs[@"agentID"] isKindOfClass:NSString.class]) {
    agentIDValue = ((NSString*)config.rawPrefs[@"agentID"]).integerValue;
  }
  return @{
    @"touser" : (touser && [touser length] != 0) ? touser : @"@all",
    @"msgtype" : @"text",
    @"agentid" : @(agentIDValue),
    @"text" : @{
      @"content" : XStr(@"%@\n%@", context.title ?: @"", context.message ?: @"")
    },
    @"safe" : @0
  };
}
```

> **给新服务的启示**：如果目标服务的某个字段对类型有硬性要求（整数、数组等），
> 在 `infoDictForBulletinContext:config:` 里做转换，而不是依赖用户填对。

### 4.5 异步 URL：先拿 access_token，再拼最终 URL

企业微信的最终 URL 依赖一个需要先请求的凭证。Pusher 的做法是覆写**异步**版
`URLStringForConfig:completion:`——基类的异步默认实现会自动调用同步版，
两者互不干扰；只有「拿 URL 必须发网络请求」的服务才需要覆写异步版。

`Core/Services/NSPWechatService.m`（完整代码，逐段讲解）：

```objc
// ---------------------------------------------------------------
// token 缓存:企业微信 access_token 有效期约 7200 秒。
// 缓存它,避免每条通知都重新请求(还会触发频率限制);
// 并且失败的 gettoken 绝不会把空 token 写进缓存污染重试路径。
//
// 重要:必须是文件级 static,不能是函数级 static!
// 函数级 static 会让读写两套字典,缓存永远不命中,每条通知都重新请求 token。
// ---------------------------------------------------------------
static NSMutableDictionary* wechatTokenCache = nil;
static NSObject* wechatTokenCacheLock = nil;
static dispatch_once_t wechatTokenCacheOnceToken;

static void wechatTokenCacheInit(void) {
  dispatch_once(&wechatTokenCacheOnceToken, ^{
    wechatTokenCache = [NSMutableDictionary new];
    wechatTokenCacheLock = [NSObject new];
  });
}

static NSString* cachedWechatTokenForKey(NSString* cacheKey, BOOL* hit) {
  wechatTokenCacheInit();
  @synchronized(wechatTokenCacheLock) {
    NSDictionary* entry = wechatTokenCache[cacheKey];
    if (entry && [entry[@"expire"] timeIntervalSinceNow] > 0) {
      *hit = YES;
      return entry[@"token"];
    }
  }
  *hit = NO;
  return nil;
}

static void cacheWechatTokenForKey(NSString* cacheKey, NSString* token) {
  wechatTokenCacheInit();
  if (!token || token.length == 0) {
    return; // 绝不缓存空/失败的 token
  }
  // 按 7200s 有效期留 60s 余量,避免 token 刚过期就发请求。
  NSDate* expire = [NSDate dateWithTimeIntervalSinceNow:7200 - 60];
  @synchronized(wechatTokenCacheLock) {
    wechatTokenCache[cacheKey] = @{@"token" : token, @"expire" : expire};
  }
}

+ (void)URLStringForConfig:(NSPushServiceConfig*)config
                completion:(void (^)(NSString* urlString))completion {
  NSString* corpid = config.rawPrefs[@"corpid"];
  NSString* corpsecret = config.rawPrefs[@"corpsecret"];
  if (!corpid || !corpsecret) {
    if (completion) {
      completion(@""); // 空 URL 避免在请求创建时崩溃
    }
    return;
  }

  // 缓存 key 用 corpid|corpsecret 区分不同企业,避免串 token。
  NSString* cacheKey = [NSString stringWithFormat:@"%@|%@", corpid, corpsecret];
  BOOL cacheHit = NO;
  NSString* cachedToken = cachedWechatTokenForKey(cacheKey, &cacheHit);
  if (cacheHit) {
    if (completion) {
      completion([[PUSHER_SERVICE_WECHAT_URL
          stringByReplacingOccurrencesOfString:@"REPLACE_DYNAMIC_KEY"
                                    withString:cachedToken] copy]);
    }
    return;
  }

  // miss:请求 gettoken。corpid/corpsecret 按 RFC 3986 转义后拼 query。
  NSString* reqUrl = @"https://qyapi.weixin.qq.com/cgi-bin/gettoken";
  NSDictionary* params = @{@"corpid" : corpid, @"corpsecret" : corpsecret};
  NSMutableArray* queryItems = [NSMutableArray array];
  NSCharacterSet* allowed = [NSCharacterSet
      characterSetWithCharactersInString:@"ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghij"
                                         @"klmnopqrstuvwxyz0123456789-._~"];
  for (NSString* key in params) {
    NSString* encoded = [(NSString*)params[key]
        stringByAddingPercentEncodingWithAllowedCharacters:allowed];
    [queryItems addObject:[NSString stringWithFormat:@"%@=%@", key, encoded]];
  }
  NSString* queryString = [queryItems componentsJoinedByString:@"&"];
  reqUrl = [reqUrl stringByAppendingFormat:@"?%@", queryString];
  NSMutableURLRequest* request =
      [NSMutableURLRequest requestWithURL:[NSURL URLWithString:reqUrl]];
  [request setHTTPMethod:@"POST"];
  [request setValue:@"application/json" forHTTPHeaderField:@"Accept"];
  NSURLSession* session = [NSURLSession sharedSession];
  NSURLSessionDataTask* dataTask = [session
      dataTaskWithRequest:request
        completionHandler:^(NSData* data, NSURLResponse* response,
                            NSError* error) {
          NSString* token = @"";
          if (!error) {
            NSDictionary* jsonResponse =
                [NSJSONSerialization JSONObjectWithData:data
                                                options:0
                                                  error:nil];
            if ([jsonResponse[@"errcode"] isEqual:@(0)]) {
              token = jsonResponse[@"access_token"];
            }
          }
          if (token && token.length > 0) {
            cacheWechatTokenForKey(cacheKey, token);
          }
          if (completion) {
            if (!token || token.length == 0) {
              // 拿不到 token(网络错误或 corpid/corpsecret 无效)。
              // 回调 nil 而不是空串:空 URL 会进发送器的 invalid URL 分支;
              // nil 则在上层 sendToService: 的 completion 里被拦截并记日志,
              // 不会带个必败的空 token 去发请求,也不污染重试状态。
              completion(nil);
              return;
            }
            completion([[PUSHER_SERVICE_WECHAT_URL
                stringByReplacingOccurrencesOfString:@"REPLACE_DYNAMIC_KEY"
                                          withString:token] copy]);
          }
        }];
  [dataTask resume];
}
```

三个重点：

- **缓存要文件级 static**（见代码注释，Function-scope static 会导致读写两套字典，
  缓存永远不命中）；
- **失败回调 nil 而不是空串**：空 URL 会进 `NSPushRequestSender` 的 invalid URL 分支；
  nil 则直接在上层 `sendToService:` 的 completion 里被拦截并记日志；
- 发送侧（`NSPusher`）本来就是「URL 回调到了才真正发送」的异步设计，
  所以不需要动任何核心代码。

### 4.6 每应用覆盖：让不同 App 发到不同的人

企业微信允许用户**按 App** 指定 `touser`（比如微信通知发给「张三」、
QQ 通知发给「李四」）。这一步需要三处配合：

**① 服务类：声明每应用字段** `extraCustomAppPrefsForName:appPrefs:`

```objc
+ (NSDictionary*)extraCustomAppPrefsForName:(NSString*)name
                                    appPrefs:(NSDictionary*)appPrefs {
  return @{@"touser" : appPrefs[@"touser"] ?: @""};
}
```

> 这个字段会被合进单个 App 的覆盖配置（`BuiltInServices[Wechat][customApps][<appID>]`），
> 发送时 `effectiveConfigForAppID:` 把它 merge 进 `config.rawPrefs`，
> 所以 `infoDictForBulletinContext:config:` 里读 `touser` 就能拿到覆盖值。

**② Preferences：注册这个字段的 specifier**

`Preferences/NSPSharedSpecifiers.m` 的 `get:withAppID:isCustomService:` 里
给服务加一个分支：

```objc
} else if (XEq(service, PUSHER_SERVICE_WECHAT)) {
  return [NSPSharedSpecifiers wechat:appID];
}
```

对应的方法（完整代码见 `NSPSharedSpecifiers.m` 的 `+wechat:`）：
创建一个 `Touser` 的 `PSEditTextCell`，`key` 用
`NSPPreferenceServiceTouserKey`，`service` 用 `PUSHER_SERVICE_WECHAT`。

> 只在自定义 App 控制器里需要额外字段时才碰 NSPSharedSpecifiers；
> 普通服务（包括 Bark）完全不用动它。

**③ plist：加 App Customization 入口**

`Wechat.plist` 里在 Apps 组后面加：

```xml
<dict>
	<key>cell</key>
	<string>PSLinkCell</string>
	<key>label</key>
	<string>App Customization</string>
	<key>icon</key>
	<string>app_list</string>
	<key>detail</key>
	<string>NSPCustomizeAppsController</string>
	<key>service</key>
	<string>Wechat</string>
	<key>defaultTouserKey</key>
	<string>touser</string>
</dict>
```

### 4.7 企业微信的设置界面：Wechat.plist

结构上比 Bark.plist 多三样东西：

1. **Credentials 组**：三个输入框 `corpid` / `corpsecret` / `agentID`
   （都是 `PSEditTextCell` + `service=Wechat`，写法与 Bark 完全一致）；
2. **App Customization 入口**（见 4.6 ③）；
3. **Options 组**：一个带 `footerText` 的说明段，告诉用户
   `touser` 的格式（`"Tom|Jerry"` 用 `|` 分隔，留空默认 `@all`）：

```xml
<dict>
	<key>cell</key>
	<string>PSGroupCell</string>
	<key>label</key>
	<string>Options</string>
	<key>footerText</key>
	<string>Use touser to specify message recipients.
Separate usernames with "|", like "Tom|Jerry". Default is "@all" for all users. Leave blank for "@all".</string>
</dict>
```

> **给新服务的启示**：字段多的时候，用 `footerText` 把格式要求写在设置里，
> 用户不用翻文档。

### 4.8 小结：企业微信 = Bark + 全部进阶写法

| 进阶能力 | 企业微信的实现 |
| --- | --- |
| 异步 URL（动态 token） | 覆写 `URLStringForConfig:completion:`，文件级 static 缓存 + 7200s 余量 |
| 多服务特有字段 | `extraPrefsForName:` 返回 corpid/corpsecret/agentID/touser |
| 每应用覆盖 | `extraCustomAppPrefsForName:` + `NSPSharedSpecifiers` 分支 + plist 入口 |
| 请求体类型转换 | `agentid` 字符串 → `NSNumber` 整数 |
| 失败语义 | 拿不到 token 回调 `nil` |
| 复杂设置界面 | 输入框 + App Customization + Options footerText |

## 6. 协议方法速查表（`NSPPushService` / `NSPushServiceBase`）

| 方法 | 必须? | 基类默认 | 干什么 | 参考实现 |
| --- | --- | --- | --- | --- |
| `+serviceName` | ✅ 必须 | 返回 nil | 注册名，与 `BUILTIN_PUSHER_SERVICES`、plist 文件名一致 | 所有服务 |
| `+loopPreventionAppID` | 可选 | `@""` | 返回「自己的 iOS App」的 bundle id，该 App 的通知不再转发给自己，防无线循环 | Pushover / Pushbullet |
| `+infoDictForBulletinContext:config:` | ✅ 必须 | 共享 data dict（OC 字典） | 组装请求体（POST 时为 JSON body；GET 时拼成 query） | **Bark**（最简）、**企业微信**（类型转换/touser） |
| `+URLStringForConfig:completion:` | 二选一 | 同步调用下面的同步方法 | 异步取最终 URL（如企业微信 token）后再回调 | **企业微信** |
| `+URLStringForConfig:` | 二选一 | 抛异常（强制子类实现） | 同步生成最终 URL，通常做 REPLACE_KEY 替换 | **Bark**、除 Wechat 外全部 |
| `+headersForConfig:` | 可选 | `@{}` | 认证/自定义 Header | Pushbullet（Access-Token）、Pusher Receiver（x-apikey） |
| `+extraPrefsForName:servicePrefs:` | 可选 | `@{}` | 声明服务特有字段并给默认值 | **Bark**（serverURL）、**企业微信**（corpid/secret/agentID/touser） |
| `+extraCustomAppPrefsForName:appPrefs:` | 可选 | `@{}` | 声明「每应用覆盖」字段 | **企业微信**（touser） |
| `+urlForEventName:dbName:serverURL:` | 可选 | `@""` | 读配置阶段拼 URL 模板（可含占位符） | IFTTT、Pusher Receiver、**Bark** |
| `+shouldIncludeIconForConfig:` | 可选 | NO | 是否给请求体加 App 图标（Base64） | Custom Service |
| `+shouldIncludeImageForConfig:` | 可选 | NO | 是否给请求体加通知附件图片（自动缩小） | Custom Service |

> 「二选一」：实现同步版即可，基类的异步默认实现会帮你包一层；
> 只有拿 URL 必须发网络请求（取 token）时才需要覆写异步版（企业微信）。

## 7. 进阶主题

### 7.1 防循环（`loopPreventionAppID`）

如果某个推送服务有自己的 iOS App（比如 Pushover、Pushbullet），
该 App 推送的通知被转发出去 → 目标 App 又收到 → 又触发通知 → 死循环。
实现该服务时返回自己 App 的 bundle id 即可：

```objc
+ (NSString*)loopPreventionAppID {
  return PUSHER_SERVICE_PUSHOVER_APP_ID; // 如 @"net.superblock.Pushover"
}
```

这个只是第一道防线；`NSPusher` 还有一个通用的标题计数防循环
（25 条滑动窗口内同标题出现 10 次才拦截），两个机制是叠加的。
Bark / 企业微信没有自己的 iOS App，不需要实现。

### 7.2 图标与图片（把附件一起推出去）

基类 `baseInfoDictForBulletinContext:config:` 已经包含：
`deviceName / appName / appID / title / subtitle / message / date`，以及
开启后追加的 `icon`（App 图标 Base64）和 `image`（通知附件，自动缩放）。

```objc
+ (BOOL)shouldIncludeIconForConfig:(NSPushServiceConfig*)config {
  // 让用户在设置里勾选(存成 includeIcon)
  NSNumber* includeIcon = config.rawPrefs[@"includeIcon"];
  return includeIcon && includeIcon.boolValue;
}
```

注意：

- `image` 在发送器里会被自动转 Base64；若目标服务不接受
  `[Base64 Image String]` 或裸 `@YES` 标记，自己裁剪 dict 时记得摘掉。
- 图片有默认缩放宽高（1000×1000）；用户可配置 `imageMaxWidth/imageMaxHeight/`
  `imageShrinkFactor` 覆盖。
- 如果服务只需要标题/正文，直接像 Bark 这样写一个精简 dict 就行，
  完全不必调用 super（省得把 `image`/`icon` 这类字段带进 body）。

### 7.3 请求报文的两个硬限制（务必先确认目标服务能接受）

`NSPushRequestSender` 只支持两种形态：

| method | 形态 |
| --- | --- |
| POST（默认） | `application/json` body（字典 JSON 序列化），自动带 Accept / Content-Type / Content-Length |
| GET | 把 dict 按 RFC 3986 转义拼进 query 串 |

> 默认 method 是 POST；`NSPusher` 里
> `XStrDefault(effectiveConfig.rawPrefs[@"method"], @"POST")`，
> 服务可以在 `extraPrefsForName:` 里声明一个 `method` 字段让用户/服务切换 GET。

所以：

- **只接受 form 编码的表单服务（如很多 webhook / 传统 Server酱）当前不直接支持**，
  选择示例服务前先确认它的 API 是 JSON 或 GET query；
- 实在绕不开，最合适的做法是给 `NSPushRequestSender` 增加对
  `application/x-www-form-urlencoded` 的支持（顺着现在的 POST 分支加），
  属于核心组件改动，建议先开 issue 讨论再动。

### 7.4 其它值得知道的既定行为（来自核心组件，服务侧无需处理）

- 每次分发在后台队列执行（`QOS_CLASS_USER_INITIATED`），过滤决策在主线程，不卡 SpringBoard；
- 失败自动重试 5 次（`PUSHER_TRIES`），网络错误间隔 1 秒，图片过大重试间隔 3 秒；
- URL 超时 10 秒，失败/成功都会写入设置里的日志页，UI 上每个服务还有
  「Send Test Notification」一键验证；
- 每应用覆盖通过 `effectiveConfigForAppID:` 合并（appID 大小写不敏感），
  服务类在 `infoDictForBulletinContext:config:` 里读到的就是合并后的值。

## 9. 常见问题

**Q:写好了但设置里看不到我的服务?**
A:多半是 `serviceName` 字符串与 `BUILTIN_PUSHER_SERVICES` 里的不一致，或 Preferences
   bundle 没重新编译（记得 `make clean`）。

**Q:日志显示 URL 正常但对方一直没收到?**
A:开日志逐项核对 Method / Header / Request Body Dictionary；再确认服务端接受
   JSON（POST）而非表单；最后看 Network Response 里的错误码（401/403 一般代表认证字段名不对）。

**Q:可以直接 Copy 现有服务改吗?**
A:可以，推荐顺序：**Bark**（最简，90% 的场景）→ Feishu（超简）→
   Pushover（字段多的 body）→ **企业微信**（异步 URL + 每应用覆盖的完整样板）。

**Q:我想做一个「半自定义」服务，用户自己填 URL?**
A:这其实就是内置「Custom Service」在做的事，直接引导用户用那个；内置服务应面向
   固定 API 的服务商。

**Q:为什么我的服务要像企业微信那样异步取 token?**
A:只有当最终 URL 依赖一个必须先网络请求才能拿到的凭证时才需要。如果凭证是
   用户配置的静态值（key / token 字段），实现同步 `URLStringForConfig:` 就够了，
   基类会自动帮你包一层异步。
