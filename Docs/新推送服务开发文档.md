# Pusher 新推送服务开发文档(以 ntfy.sh 为例)

> 本文档面向想要为 Pusher 添加「新内置推送服务」的开发者。
> 整篇用一个完整的真实示例(**ntfy.sh**)贯穿:从注册常量、编写服务类、
> 到添加设置界面、编译测试,最后再给出一批进阶写法。
> 读完本文档,你应该能照着这套流程在 30 分钟内接入任意一个新的推送服务。

## 2. Pusher 是怎么推送的(架构速览)

### 2.1 数据流

```
SpringBoard 收到一条系统通知
        │
        ▼
Tweak.xm 里的 BBServer hook (sendBulletinToPusher:)
        │
        ▼
NSPusher.handleBulletin:   ← 入口,单例
   ├─ 全局预置过滤 (NSPushFilter / globalAppList / 锁屏&网络条件)
   ├─ 防循环 (PUSHER_LOOP_PREVENTION_WINDOW=25, THRESHOLD=10)
   └─ 逐服务分发 sendToService:  (只发给已启用的服务)
        │
        ▼
服务类 (实现 NSPPushService 协议)
   ├─ infoDictForBulletinContext:config:  → 组装请求体
   ├─ headersForConfig:                   → 组装认证 Header
   └─ URLStringForConfig:completion:      → 组装最终 URL(可能异步)
        │
        ▼
NSPushRequestSender   ← 统一发送器
   ├─ 失败重试 (PUSHER_TRIES=5, 间隔 1~3 秒)
   ├─ 图片过大自动缩小重发
   └─ NSPushLog 记录每一步日志
```

### 2.2 代码地图(与本章节相关的文件)

| 文件 | 职责 |
| --- | --- |
| `Core/NSPushService.h` | `NSPPushService` 协议 + `NSPushServiceBase` 基类 + `NSPushServiceManager` 注册表 |
| `Core/NSPushService.m` | 基类默认实现、共享 data dict 构建、注册表逻辑 |
| `Core/Services/` | 每个内置服务一个 `NSP<Xxx>Service.h/.m`,**新服务放这里** |
| `Core/NSPusher.m` | 入口,`sendToService:` 逐服务流水线 |
| `Core/NSPushConfig.m` | 读取 Preferences 并组装 `NSPushServiceConfig`(含调用 `urlForEventName:`) |
| `Core/NSPushRequestSender.m` | 实际发 HTTP 请求(JSON body / GET query + 重试) |
| `Generated/BuiltinServices.generated.h` | 构建期自动生成:import 所有内置服务头文件并给出 `BUILTIN_PUSHER_SERVICES` 名单 |
| `global.h` | 通用常量(重试次数、SNS 字段名等)。服务名/URL 宏已下沉到各自的 `NSP<Xxx>Service.h` |
| `Preferences/Resources/<服务名>.plist` | 每个服务的设置界面布局 |
| `Preferences/NSPSharedSpecifiers.m` | 每应用覆盖字段的注册(只有需要时才改) |

### 2.3 服务的「注册制」——为什么加服务不用碰核心代码

Pusher 的服务是**自注册**的,核心代码对你零依赖:

1. 每个服务类在 `+load` 里调用
   `[NSPushServiceManager registerServiceClass:self forName:[self serviceName]];`
2. `NSPushServiceManager` 维护一个 `name -> Class` 的字典;
   查不到名字时兜底返回 `NSPCustomService`(自定义服务)。
3. `Makefile` 用通配符编译 `Core/*.m` 和 `Core/Services/*.m`,
   **新增 `.m` 文件不需要改 Makefile**。
4. `Preferences/NSPServiceListController` 遍历 `BUILTIN_PUSHER_SERVICES` 生成服务列表,
   只要服务名出现在名单里,设置里就自动出现入口。
5. `BUILTIN_PUSHER_SERVICES` 是**构建期自动生成**的:每次构建前
   `scripts/generate_builtin_services.sh` 扫描 `Core/Services/NSP*Service.h`
   里各服务自己的 `PUSHER_SERVICE_*` 名字宏,自动生成
   `Generated/BuiltinServices.generated.h`(它同时 import 所有内置服务
   头文件并给出名单)。**import 列表和名单都不需要手工维护**。

所以「添加一个新内置服务」本质只有两件事:**写一个类** + **在类自己的头文件里声明
名字宏**(import 和名单自动跟上),外加一份可选的设置界面 plist。

## 3. 我们的示例:ntfy.sh

### 3.1 为什么选它

- API 极简:一条 `POST`,无 OAuth、无签名、无回调。
- 三种能力刚好覆盖协议里的三个典型扩展点:
  - **URL 占位符替换**(topic 放进路径);
  - **Header 认证**(Bearer Token);
  - **自定义 body 字段**(tags / priority)。
- 可选私服部署 → 顺便演示 `serverURL` 覆盖(和 Bark 一致)。

### 3.2 ntfy.sh 的 API

```
POST https://ntfy.sh/<topic>

Header:
  Authorization: Bearer <access_token>   (可选,只读/topic 需要)

Body (application/json):
{
  "title":   "通知标题",
  "message": "通知内容",
  "tags":    ["iphone", "pusher"]        (可选)
}
```

结论:**topic** 放 URL 路径 → 用通用字段 `key` 存; **access_token** → 用通用字段
`token` 存; **tags** → 服务特有字段,自己定义(见 4.2)。

## 4. 动手:把 ntfy.sh 加进 Pusher

### Step 1 — 在服务自己的头文件里注册常量

每个内置服务的常量都归该服务自己管(定义在它的 `.h` 里),`global.h` 不再集中存放。
照葫芦画瓢,在 `NSPntfyService.h` 中加:

```objc
// 1) 服务名宏(必须全局唯一,同时用于 Preferences 里的 BuiltInServices key)
#define PUSHER_SERVICE_NTFY @"Ntfy"

// 2) URL 模板宏:写死默认服务地址。REPLACE_KEY 是约定的占位符,
//    最终由服务的 URLStringForConfig: 在发送时替换成用户配置的 key。
#define PUSHER_SERVICE_NTFY_URL @"https://ntfy.sh"
```

**到这里 Step 1 就结束了,import 和名单都不用你管。** 构建时
`scripts/generate_builtin_services.sh` 会自动扫这个宏,生成
`Generated/BuiltinServices.generated.h`(自动 import 你的服务头文件、
并把服务名加进 `BUILTIN_PUSHER_SERVICES`),这个名单同时驱动:

- 服务注册表的枚举
- Preferences 服务列表界面(NSPServiceListController)
- 配置快照加载(NSPushConfig)

> 原理:脚本只认「`#define PUSHER_SERVICE_XXX @"..."` 且名字不以 `_URL`/`_APP_ID`
> 结尾」的宏,所以你可以在头文件里随便加 URL / APP_ID 等变体,不会误进名单。

> `REPLACE_KEY` 是项目里的通用约定(Feishu、Bark、Pushover 都用它)。
> 需要多个占位符的服务可以自定,如 IFTTT 用 `REPLACE_EVENT_NAME`、
> Pusher Receiver 用 `REPLACE_DB_NAME`、企业微信用 `REPLACE_DYNAMIC_KEY`。
> 规则:**URL 模板里写什么占位符,`URLStringForConfig:` 里就替换什么。**

### Step 2 — 编写服务类

在 `Core/Services/` 新建 `NSPntfyService.h` 和 `NSPntfyService.m`。

**NSPntfyService.h**

```objc
#import "../NSPushService.h"

#define PUSHER_SERVICE_NTFY @"Ntfy"
#define PUSHER_SERVICE_NTFY_URL @"https://ntfy.sh"

// ntfy.sh 推送服务。
// 对应协议:https://docs.ntfy.sh/publish
@interface NSPntfyService : NSPushServiceBase

@end
```

**NSPntfyService.m**(核心文件,逐段讲解)

```objc
#import "NSPntfyService.h"
#import "../../helpers.h"        // XStr / XEq / XLog 宏
#import "../NSPushConfig.h"      // NSPushServiceConfig
#import "../NSPushSupport.h"     // NSPBulletinContext

@implementation NSPntfyService

// ---------------------------------------------------------------
// 注册:进程启动时 +load 会跑,把本类挂进 NSPushServiceManager。
// 注意要写 [self serviceName],不要硬编码字符串,保持单一事实来源。
// ---------------------------------------------------------------
+ (void)load {
  [NSPushServiceManager registerServiceClass:self forName:[self serviceName]];
}

// 注册名:必须与 NSPntfyService.h 的宏一致(大小写敏感),
// 同时决定 Preferences 里 plist 的文件名,见 Step 3。
+ (NSString*)serviceName {
  return PUSHER_SERVICE_NTFY;
}

// ---------------------------------------------------------------
// URL 模板构建:在「读配置阶段」被 NSPushConfig 调用,生成服务的基础
// url 存进 servicePrefs[@"url"]。serverURL 非空时用于自建 ntfy 私服。
// 返回的字符串可以继续保留 REPLACE_KEY,发送前才会被替换。
// ---------------------------------------------------------------
+ (NSString*)urlForEventName:(NSString*)eventName
                      dbName:(NSString*)dbName
                   serverURL:(NSString*)serverURL {
  NSString* baseURL = (serverURL && serverURL.length > 0)
                          ? serverURL
                          : PUSHER_SERVICE_NTFY_URL;
  if ([baseURL hasSuffix:@"/"]) {
    return [baseURL stringByAppendingString:@"REPLACE_KEY"];
  }
  return [baseURL stringByAppendingFormat:@"/REPLACE_KEY"];
}

// ---------------------------------------------------------------
// 最终 URL:发送前调用。基类会以同步方式调用它;一般服务实现这一个
// 同步方法就够了(异步进阶写法见 6.1 企业微信例子)。
// 这里把用户填的 topic 替换进 REPLACE_KEY。
// ---------------------------------------------------------------
+ (NSString*)URLStringForConfig:(NSPushServiceConfig*)config {
  NSString* key = config.rawPrefs[@"key"];
  NSString* url = config.rawPrefs[@"url"] ?: @"";
  return [url stringByReplacingOccurrencesOfString:@"REPLACE_KEY"
                                         withString:key ?: @""];
}

// ---------------------------------------------------------------
// 认证 Header:ntfy 用 Bearer Token。token 是通用字段,用户没填就
// 不带头(完全公开的 topic 不需要认证)。
// ---------------------------------------------------------------
+ (NSDictionary*)headersForConfig:(NSPushServiceConfig*)config {
  NSString* token = config.rawPrefs[@"token"];
  if (token && token.length > 0) {
    return @{ @"Authorization" : XStr(@"Bearer %@", token) };
  }
  return @{};
}

// ---------------------------------------------------------------
// 服务特有预置字段:除了通用模板外,每个服务可以声明自己的字段。
// 返回值会被合入 config.rawPrefs(发送时可直接读取)。
// 这里声明 serverURL(私服地址)和 tags(可选标签)。
// ---------------------------------------------------------------
+ (NSDictionary*)extraPrefsForName:(NSString*)name
                      servicePrefs:(NSDictionary*)servicePrefs {
  return @{
    @"serverURL" : servicePrefs[NSPPreferenceServiceServerURLKey]
        ?: @"https://ntfy.sh",
    @"tags" : servicePrefs[@"tags"] ?: @""
  };
}

// ---------------------------------------------------------------
// 请求体:ntfy 的 JSON body 只需要 title / message / tags。
// 想带更多上下文(设备名、应用名、日期、图标、图片)的话,
// 直接 [[super infoDictForBulletinContext:config:] mutableCopy]
// 再裁剪/追加,详见 6.4。
// ---------------------------------------------------------------
+ (NSDictionary*)infoDictForBulletinContext:(NSPBulletinContext*)context
                                     config:(NSPushServiceConfig*)config {
  NSMutableDictionary* body = [@{
    @"title" : context.title ?: @"",
    @"message" : context.message ?: @""
  } mutableCopy];

  NSString* tags = config.rawPrefs[@"tags"];
  if (tags && tags.length > 0) {
    // 用户在设置里填 "iphone,pusher" → 转成 JSON 数组
    body[@"tags"] = [tags componentsSeparatedByString:@","];
  }
  return body;
}

@end
```

> **关于图片**:ntfy 的 JSON body 也支持 `image`(Base64),但 Pusher 的共享 data
> dict 里 `image` 是 `UIImage`,发送器 `NSPushRequestSender` 会在发 POST 前自动
> 把它 `base64RepresentationForImage:` 序列化,所以只要实现
> `shouldIncludeImageForConfig:` 返回 YES 就能直接带图,见 6.4。

## 5. 协议方法速查表(`NSPPushService` / `NSPushServiceBase`)

| 方法 | 必须? | 基类默认 | 干什么 | 参考实现 |
| --- | --- | --- | --- | --- |
| `+serviceName` | ✅ 必须 | 抛异常 | 注册名,与 `BUILTIN_PUSHER_SERVICES`、plist 文件名一致 | 所有服务 |
| `+loopPreventionAppID` | 可选 | `@""` | 返回「自己的 iOS App」的 bundle id,该 App 的通知不再转发给自己,防无线循环 | Pushover / Pushbullet |
| `+infoDictForBulletinContext:config:` | ✅ 必须 | 共享 data dict(Object-C 字典) | 组装请求体(POST 时为 JSON body;GET 时拼成 query) | Bark(最简)、Pushover(设备/铃声) |
| `+URLStringForConfig:completion:` | 二选一 | 同步调用下面的同步方法 | 异步取最终 URL(如企业微信 token)后再回调 | Wechat |
| `+URLStringForConfig:` | 二选一 | 抛异常(强制子类实现) | 同步生成最终 URL,通常做 REPLACE_KEY 替换 | 除 Wechat 外全部 |
| `+headersForConfig:` | 可选 | `@{}` | 认证/自定义 Header | Pushbullet(Access-Token)、Pusher Receiver(x-apikey) |
| `+extraPrefsForName:servicePrefs:` | 可选 | `@{}` | 声明服务特有字段并给默认值 | Bark(serverURL)、Wechat(corpid/secret/...) |
| `+extraCustomAppPrefsForName:appPrefs:` | 可选 | `@{}` | 声明「每应用覆盖」字段 | Wechat(touser) |
| `+urlForEventName:dbName:serverURL:` | 可选 | `@""` | 读配置阶段拼 URL 模板(可含占位符) | IFTTT、Pusher Receiver、Bark |
| `+shouldIncludeIconForConfig:` | 可选 | NO | 是否给请求体加 App 图标(Base64) | Custom Service |
| `+shouldIncludeImageForConfig:` | 可选 | NO | 是否给请求体加通知附件图片(自动缩小) | Custom Service |

> 「二选一」:实现同步版即可,基类的异步默认实现会帮你包一层;
> 只有拿 URL 必须发网络请求(取 token)时才需要覆写异步版。

## 6. 进阶主题

### 6.1 异步 URL——以「企业微信 access_token」为例

有些服务 URL 本身依赖一个需要先请求的凭证。Pusher 的做法是覆写**异步**版
`URLStringForConfig:completion:`,基类的异步默认实现会自动调用同步版,两者互不干扰。

关键点(完整代码见 `Core/Services/NSPWechatService.m`,这里是骨架):

```objc
static NSMutableDictionary* wechatTokenCache;  // 必须是文件级 static!
static NSObject* wechatTokenCacheLock;

+ (void)URLStringForConfig:(NSPushServiceConfig*)config
                completion:(void (^)(NSString* urlString))completion {
  // 1) 读凭证(corpid/corpsecret)
  // 2) 命中缓存(7200s - 60s 余量)直接回调,避免每条通知都请求 token
  // 3) miss:GET https://qyapi.weixin.qq.com/cgi-bin/gettoken
  //    → 成功:写缓存,把 access_token 替换进
  //      PUSHER_SERVICE_WECHAT_URL 的 REPLACE_DYNAMIC_KEY 再回调
  //    → 失败:completion(nil); 上层会打 "Failed to build URL" 并跳过发送
  //      (比带个空 token 必败的请求好,也不会污染重试状态)
}
```

三个重点:

- **缓存要文件级 static**(见代码注释,Function-scope static 会导致读写两套字典,
  缓存永远不命中);
- **失败回调 nil 而不是空串**:空 URL 会进 `NSPushRequestSender` 的 invalid URL 分支;
  nil 则直接在上层 `sendToService:` 的 completion 里被拦截并记日志;
- 发送侧(6.2 里的 `NSPusher`)本来就是「URL 回调到了才真正发送」的异步设计,
  所以不需要动任何核心代码。

### 6.2 服务特有字段 + 每应用覆盖

- **服务级特有字段**用 `extraPrefsForName:servicePrefs:`
  (本示例 Step 2 的 `tags` 就是这么来的,企业微信更进一步声明了
  corpid / corpsecret / agentID / touser 四个)。
- **每应用覆盖**用 `extraCustomAppPrefsForName:appPrefs:`:某些服务允许
  用户针对某个 App 单独改参数(如企业微信的 `touser` 可以按 App 指定接收人)。
  需要在 `Preferences/NSPSharedSpecifiers.m` 的 `get:withAppID:` 里
  给服务加一个分支,返回该服务的自定义 App 字段 specifiers
  (参考其中的 `wechat:` 方法)。

> 只在自定义 App 控制器里需要额外字段时才碰 NSPSharedSpecifiers;
> 普通服务(包括本示例)完全不用动它。

### 6.3 防循环(`loopPreventionAppID`)

如果某个推送服务有自己的 iOS App(比如 Pushover、Pushbullet),
该 App 推送的通知被转发出去 → 目标 App 又收到 → 又触发通知 → 死循环。
实现该服务时返回自己 App 的 bundle id 即可:

```objc
+ (NSString*)loopPreventionAppID {
  return PUSHER_SERVICE_PUSHOVER_APP_ID; // 如 @"net.superblock.Pushover"
}
```

这个只是第一道防线;`NSPusher` 还有一个通用的标题计数防循环
(25 条窗口内同标题出现 10 次才拦截),两个机制是叠加的。

### 6.4 图标与图片(把附件一起推出去)

基类 `baseInfoDictForBulletinContext:config:` 已经包含:
`deviceName / appName / appID / title / subtitle / message / date`,以及
开启后追加的 `icon`(App 图标 Base64)和 `image`(通知附件,自动缩放)。

```objc
+ (BOOL)shouldIncludeIconForConfig:(NSPushServiceConfig*)config {
  // 让用户在设置里勾选(存成 includeIcon)
  NSNumber* includeIcon = config.rawPrefs[@"includeIcon"];
  return includeIcon && includeIcon.boolValue;
}
```

注意:

- `image` 在发送器里会被自动转 Base64;若目标服务不接受
  `[Base64 Image String]` 或裸 `@YES` 标记,自己裁剪 dict 时记得摘掉。
- 图片有默认缩放宽高(1000×1000);用户可配置 `imageMaxWidth/imageMaxHeight/`
  `imageShrinkFactor` 覆盖。
- 如果服务只需要标题/正文,直接像本示例这样写一个精简 dict 就行,
  完全不必调用 super(省得把 `image`/`icon` 这类字段带进 body)。

### 6.5 请求报文的两个硬限制(务必先确认目标服务能接受)

`NSPushRequestSender` 只支持两种形态:

| method | 形态 |
| --- | --- |
| POST(默认) | `application/json` body(字典 JSON 序列化),自动带 Accept / Content-Type / Content-Length |
| GET | 把 dict 按 RFC 3986 转义拼进 query 串 |

所以:

- **只接受 form 编码的表单服务(如很多 webhook / 传统 Server酱)当前不直接支持**,
  选择示例服务前先确认它的 API 是 JSON 或 GET query;
- 实在绕不开,最合适的做法是给 `NSPushRequestSender` 增加对
  `application/x-www-form-urlencoded` 的支持(顺着现在的 POST 分支加),
  属于核心组件改动,建议先开 issue 讨论再动。

### 6.6 其它值得知道的既定行为(来自核心组件,服务侧无需处理)

- 每次分发在后台队列执行(`QOS_CLASS_USER_INITIATED`),过滤决策在主线程,不卡 SpringBoard;
- 失败自动重试 5 次(`PUSHER_TRIES`),网络错误间隔 1 秒,图片过大重试间隔 3 秒;
- URL 超时 10 秒,失败/成功都会写入设置里的日志页,UI 上每个服务还有
  「Send Test Notification」一键验证。

## 8. 常见问题

**Q:写好了但设置里看不到我的服务?**
A:多半是 `serviceName` 字符串与 `BUILTIN_PUSHER_SERVICES` 里的不一致,或 Preferences
   bundle 没重新编译(记得 `make clean`)。

**Q:日志显示 URL 正常但对方一直没收到?**
A:开日志逐项核对 Method / Header / Request Body Dictionary;再确认服务端接受
   JSON(POST)而非表单;最后看 Network Response 里的错误码(401/403 一般代表认证字段名不对)。

**Q:可以直接 Copy 现有服务改吗?**
A:可以,推荐顺序:Bark(最简)→ Feishu(超简)→ Pushover(字段多的 body)→ Wechat(异步 URL)。

**Q:我想做一个「半自定义」服务,用户自己填 URL?**
A:这其实就是内置「Custom Service」在做的事,直接引导用户用那个;内置服务应面向
  固定 API 的服务商。
